# Черновик до подтверждения email

Реализация от 3 сентября 2026 года. Дополняет `MANAGE_ACCESS_SECURITY_2026-09-01.md`: подтверждённый владелец по-прежнему нужен для приглашения участников, оплаты, передачи и настроек доступа. Исключение — редактирование собственного нового неоплаченного черновика в браузере, где он создан.

## Сценарий

1. «Создать открытку» открывает редактор сразу. Авторизованному организатору новый черновик сразу закрепляется за его уже подтверждённым email.
2. Для гостя сервер выдаёт подписанный технический HttpOnly cookie `slv_draft_session`. Адрес редактора содержит ID карточки и сам по себе не даёт доступа.
3. В основе открытки гость указывает email. Данные сохраняются, а владение остаётся неподтверждённым до перехода по одноразовой ссылке из письма. Ошибка отправки письма не отменяет сохранение основы; отправку можно повторить.
4. До подтверждения доступны оформление, тексты, фотографии и предпросмотр своего черновика. Открытие сбора и голосования, оплата, передача и изменение настроек владельца требуют обычной проверки подтверждённого доступа на сервере.
5. Подтверждение атомарно закрепляет владельца и выдаёт сессию организатора. После этого гостевой cookie перестаёт давать доступ к карточке, даже если его срок ещё не истёк.

## Границы безопасности

- Гостевой доступ включается явно через `allowGuestDraft: true` только у редактора, предпросмотра и необходимых операций с черновиком. Проверка доступа по умолчанию остаётся закрытой для гостей.
- Cookie подписан HMAC-SHA256 с отдельным назначением подписи. Токены сессии организатора и гостевого черновика не взаимозаменяемы. Используется существующий `ORGANIZER_SESSION_SECRET`; новых переменных окружения и миграций нет.
- Cookie имеет HttpOnly, SameSite=Lax, Secure в production. До 10 отдельных разрешений, каждое на конкретный ID и максимум на 7 дней от создания. Создание нового черновика не продлевает старые разрешения. При превышении 10 сохраняются последние 10. Очистка cookie лишает гостя доступа до входа по email.
- Выдать разрешение можно только после серверного создания новой карточки. ID из пользовательского запроса для выдачи разрешения не используется.
- Карточка должна быть без владельца, с состояниями DRAFT / UNPAID / PREPARING, без признаков прежнего открытия сбора, оплаты, передачи, административного доступа, скрытия или удаления.
- Изменение данных основы не обновляет `organizer_email`. Сохранение, начатое до подтверждения, не может сбросить уже закреплённого владельца.
- Новый запрос первичного подтверждения аннулирует предыдущие неиспользованные ссылки для этой карточки. В PostgreSQL замена сериализована транзакцией и advisory lock. Потребление ссылки одноразовое, закрепление владельца условное: только если владельца ещё нет.
- Права существующих владельцев и сотрудников, запрет support на управление и production-запрет локального обхода сохранены. Существующие ограничения частоты отправки почты и создания карточек продолжают действовать.
- Если создатель нового черновика одновременно вошёл как admin/moderator, в редакторе приоритет имеет разрешение на свой гостевой черновик: поле email остаётся доступным, а сохранение отправляет первичное подтверждение. Служебная сессия без такого разрешения не даёт права назначить владельца; пустой адрес в этом случае явно обозначен как неподтверждённый. Проверка support остаётся раньше гостевой проверки.

## Проверки

- `draft-session.test.ts`: подделка подписи/ID, чужая карточка, отсутствие и истечение cookie, разделение назначения токенов, ограничения состояния карточки, права владельца и сотрудников.
- `guest-draft-security.test.ts`: реальные проверки разрешений в действиях и API, сохранение без преждевременного назначения владельца, отказ открыть сбор/голосование, оплатить и передать карточку, успешный и конфликтующий claim.
- `basics-settings-form.test.tsx`: обязательное поле email для гостя, восстановление ожидающего подтверждения, повторная отправка после ошибки и обновление после подтверждения.
- `draft-ownership.live.test.ts`: интеграционные проверки реальных репозиториев PostgreSQL в изолированных временных таблицах. Сохранение основы после claim не меняет владельца; заменённая ссылка не работает, новая потребляется только один раз.

Запуск проверки PostgreSQL: `$env:RUN_DRAFT_ACCESS_DB_TEST='1'; node --env-file=.env.local node_modules/vitest/vitest.mjs run src/lib/manage/draft-ownership.live.test.ts`. Рабочие данные и реальные письма в этом тесте не используются. Без переменной тест пропускается.

Предрелизная проверка: 1137 тестов прошли в полном coverage-прогоне, дополнительно 2 PostgreSQL-теста во временных таблицах; typecheck, lint и production build успешны. Регрессия одновременного входа создателя и admin/moderator проверена на уровне actor-check и реального server action с мокированным почтовым транспортом.
