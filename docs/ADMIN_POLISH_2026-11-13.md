## Заключение об атрибуции

Проверка выполнена на локальном приложении и отдельной тестовой PostgreSQL на порту 5441. Production-БД не исследовалась и не изменялась.

Установлено:

- В исходном демонстрационном наборе 23 открытки, учитываемые как реальные в отчёте, созданы SQL-наполнением (`qa-public-*`). Только у одной была сохранена запись входа. Поэтому прежние неизвестные источники и отсутствие просмотров на локальных скриншотах объяснялись составом тестовых данных, а не доказывали ошибку передачи источника.
- Главная и все пять SEO-страниц действительно сохраняют просмотры. Для `/gruppovaya-otkrytka/novyy-god` подтверждены сохранение UTM после согласия, обновление страницы, переход к примеру и создание из примера.
- Первый вход сохраняется при создании через новую вкладку `/manage/new` и после реальной проверки одноразового токена авторизации. Отправка писем для этой проверки не выполнялась: одноразовый токен был создан в изолированной тестовой БД и использован штатным маршрутом проверки.
- При недоступности клиентского приёма телеметрии серверное событие создания всё равно содержит ранее сохранённый первый вход. Отсутствие просмотров при ненулевых созданиях поэтому само по себе не означает потерю атрибуции.
- При отказе от аналитики источник не выдумывается.
- Прямой вход на `/example` без ранее сохранённого маркетингового входа остаётся неопределённым в отчёте источников. Существующая модель первого входа охватывает главную и пять SEO-страниц; демо-события `/example` не объявляются первой маркетинговой страницей. Переход SEO → `/example` → создание сохраняет исходную SEO-страницу. Методика не расширялась в рамках полировки.
- Связь оплаты с исходной новогодней страницей проверена на синтетической записи подтверждённой оплаты в тестовом журнале и в настоящем административном отчёте. Robokassa и реальные денежные операции не вызывались. Условия признания боевой оплаты дополнительно покрыты интеграционными тестами.

Машинный результат 13 сценариев: [attribution.json](C:/Project/Поздравления2.0/output/admin-polish/attribution.json). Созданные проверкой открытки явно помечены тестовыми по известным ID. Исторические источники не восстанавливались предположениями.

Нельзя достоверно восстановить отсутствующий первый вход у старых записей, отказавшихся от согласия пользователей, после потери/истечения cookie или между разными браузерами и устройствами. Просмотры без идентификатора посетителя нельзя превратить в уникальных посетителей или безусловно связать с созданием. Неизвестный источник не подменяется «Прямым переходом».

## Диагностика ошибок и ограничения данных

`telemetry_events.id` — ID события, `error_id` — корреляционный идентификатор для поиска в логах. Оба могут быть UUID и не являются кодом причины. Реальный код показывается отдельно только при наличии разрешённого сохранённого значения `errorCode`/`code`.

В подробности передаются ID, время, тип события, известная операция/класс/код, числовые диагностические поля и проверенные ссылки на существующие объекты. Произвольный контекст, сообщения исключений, email, токены, ключи, пароли, URL управления и строки подключения не передаются клиенту. В исторических данных полного описания причины обычно нет — интерфейс сообщает «Причина не сохранена». Статус «Не исправлена» не присваивается: факта устранения модель не хранит.

Отдельного события завершения подготовки открытки нет; строгая последовательная воронка не создавалась. Создание открытки после напоминания по-прежнему не отслеживается. Эти ограничения сохранены в раскрываемых пояснениях.
