Итерация 2. Очистка импорта, подтверждение и устойчивость
Цель

Точечно доработать существующий поток добавления варианта подарка по ссылке или тексту:

ввод ссылки/текста → импорт данных → проверка пользователем → создание варианта.

В рамках этой итерации необходимо:

улучшить очистку импортированных данных;
никогда не создавать вариант сразу после импорта;
сохранять исходный ввод и черновик при ошибках и переходах;
корректно обрабатывать полный, частичный и неудачный импорт;
обеспечить безопасную серверную загрузку внешних страниц;
сохранить совместимость с существующими вариантами и логикой голосования.
Важно: что не входит в эту итерацию

Не реализовывать:

проверку дубликатов по URL;
проверку похожих вариантов;
409 Conflict и GIFT_OPTION_DUPLICATE_URL;
уникальный индекс нормализованного URL;
переработку порядка источников парсинга;
полную замену существующего парсера;
изменение карточек вариантов;
изменение мобильной компоновки;
изменение редактора порядка;
изменение выпадающих меню;
изменение общего mobile footer;
изменение логики голосования;
изменение сценариев «Подарок / Бюджет»;
изменение ограничений после получения первого голоса.

Использовать интерфейс и компоненты, полученные после первой итерации.

1. Текущий поток

Сначала найти существующий путь:

пользователь открывает «Добавить вариант»;
вводит ссылку или текст;
нажимает «Заполнить карточку»;
frontend вызывает импорт;
backend загружает и разбирает страницу;
данные отображаются в форме;
пользователь подтверждает создание.

Не создавать новый параллельный поток и не переписывать архитектуру без необходимости.

2. Очистка названия товара

После извлечения данных пропускать название через отдельную функцию нормализации.

Обязательная обработка
удалить HTML-теги;
декодировать HTML-сущности:
&nbsp;;
&amp;;
&#8381;;
числовые и именованные сущности;
заменить неразрывные пробелы обычными;
удалить управляющие и невидимые символы;
схлопнуть повторные пробелы;
убрать пробелы в начале и конце;
удалить повторяющиеся части названия;
удалить служебные разделители в начале и конце:
|;
—;
-;
::;
»;
повторные разделители.
Не переносить в название
название магазина, добавленное как хвост страницы;
домен магазина;
фразы:
«купить в Москве»;
«купить в Челябинске»;
«купить с доставкой»;
аналогичные региональные и SEO-фразы;
сведения о доставке;
регион;
цену и скидку;
длинные характеристики;
хлебные крошки;
навигационные элементы;
хвосты HTML-title;
повтор названия товара;
технические фрагменты страницы.

Удалять название магазина только в случаях, когда оно явно отделено от товара разделителем или добавлено в качестве хвоста. Не удалять слово, если оно является частью реального названия товара.

Ограничение длины

Использовать существующий лимит поля.

Обрезать:

по границе слова;
после декодирования HTML-сущностей;
без разрыва Unicode-символа;
без обрезки внутри технического фрагмента или HTML-сущности.

Если дополнительные сведения полезны, переносить их в «Короткое описание».

3. Очистка остальных данных
3.1. Стоимость

Сохранять только актуальную цену товара.

Не переносить:

старую зачёркнутую цену;
размер скидки;
сумму экономии;
цену доставки;
стоимость подписки;
диапазон цен, если невозможно определить основную цену;
цену другого товара или комплектации.

Привести значение к принятому в проекте формату.

Если цена неоднозначна или не определена достоверно, оставить поле пустым. Не подставлять предположительное значение.

Не придумывать валюту, если она не была достоверно определена.

3.2. Короткое описание
удалить HTML;
декодировать HTML-сущности;
нормализовать пробелы;
удалить повтор названия;
удалить название магазина;
удалить SEO-фразы;
удалить навигацию и хлебные крошки;
удалить сведения о доставке, если они не описывают сам товар;
убрать повторяющиеся предложения;
ограничить по существующему лимиту;
обрезать только по границе слова.

Не создавать описание из случайного текста страницы.

Если после очистки остаётся бессодержательный или технический текст, оставить поле пустым.

3.3. Ссылка

Сохранять:

исходную рабочую ссылку;
либо безопасную каноническую ссылку, если она достоверно определена.

Разрешены только http и https.

При сохранении ссылки:

удалить пробелы по краям;
декодировать HTML-сущности;
удалить #fragment;
удалить рекламные параметры:
utm_*;
yclid;
gclid;
fbclid;
аналогичные параметры аналитики;
сохранить параметры, которые идентифицируют товар или его вариант;
не менять путь;
не менять ID товара;
не заменять ссылку ссылкой на категорию или главную страницу магазина.

В этой итерации очищенная ссылка не используется для проверки дубликатов.

3.4. Изображение

Использовать только допустимый URL изображения товара.

Не использовать:

favicon;
логотип магазина;
иконки интерфейса;
плейсхолдеры;
tracking pixel;
технические изображения малого размера;
data:;
file:;
локальные адреса;
неподдерживаемые форматы.

Разрешать только безопасные http и https URL.

Если есть информация о размерах изображения, отклонять явно технические изображения малого размера.

Если невозможно достоверно определить изображение товара, оставить поле пустым.

Не переделывать весь механизм выбора изображения. Добавить валидацию и очистку к уже найденному кандидату.

4. Импорт всегда создаёт черновик

После успешного импорта не создавать вариант автоматически.

Backend импорта должен возвращать данные черновика, а не сохранять новый вариант.

После получения ответа открыть существующую форму «Добавить вариант» и заполнить:

название;
примерную стоимость;
короткое описание;
ссылку;
изображение.

Вариант создаётся только после явного нажатия:

«Добавить вариант»

До этого момента импортированные данные:

не должны учитываться в числе вариантов;
не должны отображаться участникам;
не должны попадать в голосование;
не должны сохраняться как полноценный вариант.

Закрытие формы без подтверждения не создаёт вариант.

5. Состояния импорта

Использовать понятную последовательность состояний:

idle → importing → review-full / review-partial / manual / error → saving.

5.1. Загрузка

После нажатия «Заполнить карточку»:

заменить текст кнопки на «Заполняем карточку…»;
показать существующий индикатор загрузки;
заблокировать повторное нажатие;
сохранить введённую ссылку или текст;
не очищать textarea;
не закрывать окно до получения результата.

Повторное нажатие во время активного запроса не должно создавать второй запрос.

5.2. Полный успех

Полным успехом считать результат, в котором получено и прошло очистку пригодное название товара.

Открыть заполненную форму «Добавить вариант».

Дополнительное уведомление не требуется, если импорт не содержит предупреждений.

5.3. Частичный успех

Частичным считать импорт, если:

удалось получить хотя бы одно пригодное поле;
часть найденных данных была отклонена очисткой;
отсутствует название;
отсутствуют несколько ожидаемых полей;
парсер вернул неполный результат.

Открыть форму с найденными данными.

Пустые значения оставить пустыми.

Показать сообщение:

Не все данные удалось определить. Проверьте карточку перед добавлением.

Предупреждение не должно блокировать ручное заполнение и сохранение.

5.4. Неподдерживаемая или неразобранная страница

Если не удалось получить ни одного пригодного значения, показать:

Не удалось автоматически заполнить карточку. Добавьте данные вручную.

Показать действие:

«Добавить вручную»

Исходную ссылку или текст не очищать.

5.5. Ошибка сети

При timeout, сетевой ошибке, недоступности страницы или ошибке загрузки показать:

Не удалось загрузить данные. Проверьте соединение и попробуйте ещё раз.

Оставить доступными:

исправление исходного значения;
повторный импорт;
переход к ручному добавлению;
закрытие окна.

Исходный текст не очищать.

5.6. Ошибка сервера или парсера

Не показывать технический текст исключения.

Показать пользовательское сообщение:

Не удалось автоматически заполнить карточку. Добавьте данные вручную или попробуйте ещё раз.

Техническую причину записать в серверный лог.

6. Переход к ручному добавлению

При нажатии «Добавить вручную»:

не терять исходный текст;
не закрывать весь поток добавления;
открыть существующую ручную форму.

Если исходное значение является корректным URL:

перенести его в поле «Ссылка на товар».

Если введён произвольный текст:

сохранить его в состоянии черновика;
не помещать автоматически в название без явной логики;
восстановить его при возврате к окну импорта.

Если импорт был частично успешным:

сохранить все найденные данные;
заполнить ими ручную форму;
разрешить пользователю отредактировать их.

При возврате из ручной формы в окно импорта восстановить:

исходную ссылку или текст;
последний результат импорта;
пользовательские изменения, если они ещё не были подтверждены.

Предпочтительно хранить такой черновик в frontend-state. Не добавлять постоянное хранение в БД без необходимости.

7. Повторный импорт

Пользователь должен иметь возможность:

исправить ссылку;
повторить импорт;
перейти к ручному вводу;
вернуться к предыдущему шагу;
закрыть окно без создания варианта.

Повторный импорт:

не создаёт вариант;
не отправляет запрос создания;
не увеличивает счётчик вариантов;
не смешивает новые данные с результатом предыдущей страницы.
Источник значения поля

Для полей черновика учитывать происхождение:

auto — значение получено импортом;
user — значение изменено пользователем вручную.

При повторном импорте:

автоматически заменять поля с источником auto;
очищать старые автоматически найденные данные, которых нет в новом результате;
не заменять поля с источником user без предупреждения.

Если новый импорт хочет заменить изменённые вручную данные, показать компактное подтверждение:

Новый импорт может заменить данные, которые вы изменили вручную.

Действия:

«Сохранить мои изменения» — пользовательские значения остаются, остальные данные обновляются;
«Заменить импортированными» — значения заменяются новым результатом;
«Отмена» — новый импорт не применяется.

Допустима эквивалентная реализация в существующем стиле интерфейса.

Не смешивать данные двух разных товаров.

8. Безопасность серверного импортера

Все ограничения должны применяться на backend. Frontend-проверки не считаются достаточными.

8.1. Протоколы

Разрешать только:

http;
https.

Отклонять:

file;
ftp;
data;
javascript;
blob;
пользовательские схемы.
8.2. Защита от SSRF

Не обращаться к:

localhost;
127.0.0.0/8;
0.0.0.0;
приватным IPv4-сетям;
link-local адресам;
loopback IPv6;
private/local IPv6;
metadata endpoints облачных провайдеров;
внутренним именам и доменам;
адресам, которые после DNS-разрешения ведут во внутреннюю сеть.

Проверять адрес назначения:

перед первым запросом;
после каждого редиректа.

Редирект на запрещённый адрес должен прерывать импорт.

8.3. Ограничения запроса

Использовать существующие проектные настройки. Если их нет, установить разумные значения:

timeout запроса: до 8 секунд;
максимум редиректов: 3;
максимальный размер ответа: 2 МБ;
запрет бесконечного стриминга;
ограничение времени чтения ответа.

Не загружать изображения целиком только ради разбора HTML, если это не требуется текущей архитектурой.

8.4. Обработка ответа
не выполнять JavaScript страницы;
не исполнять встроенные скрипты;
не использовать небезопасный headless-browser без необходимости;
не доверять HTML до очистки;
учитывать Content-Type;
корректно обрабатывать charset;
безопасно декодировать текст;
прекращать обработку слишком большого ответа.

Получение HTTP 200 и HTML не означает успешный импорт. Успех определяется наличием пригодных данных после очистки.

8.5. Логирование

Логировать:

этап неудачи;
внутренний код ошибки;
HTTP-статус;
домен;
тип ответа;
превышение timeout или лимита размера.

Не логировать:

полный HTML;
содержимое страницы;
приватные пользовательские тексты;
токены;
cookies;
authorization headers;
чувствительные query-параметры.
9. Миграция и совместимость
В этой итерации не добавлять
поле нормализованного URL для дедупликации;
уникальный индекс URL;
глобальные или локальные ограничения уникальности;
миграцию для защиты от дубликатов.
Совместимость

Существующие варианты подарков должны:

продолжать отображаться;
редактироваться;
участвовать в голосовании;
сохранять текущие ссылки и изображения;
не требовать обязательного повторного импорта.

Новая очистка применяется:

к новым импортам;
к повторному импорту;
к данным, которые пользователь явно сохраняет после проверки.

Не выполнять массовую автоматическую очистку уже существующих вариантов.

Новые поля состояния

Состояния:

исходный ввод;
статус импорта;
происхождение поля auto/user;
предупреждение о частичном импорте;

предпочтительно хранить только во frontend-state.

Добавлять поля в БД только если без них невозможно выполнить требования. Перед миграцией проверить, нельзя ли сохранить состояние черновика локально до подтверждения.

Если миграция всё же необходима:

не делать новое поле обязательным для старых записей;
предусмотреть безопасное значение по умолчанию;
не ломать варианты без ссылки и изображения;
не изменять существующую логику голосования;
описать причину миграции в итоговом отчёте.
10. Критерии приёмки

Итерация считается выполненной, если:

SEO-заголовок страницы не сохраняется целиком как название товара.
HTML-сущности корректно декодируются.
Название не обрезается внутри HTML-сущности или слова.
Название магазина и региональный SEO-хвост удаляются.
Старая цена, скидка и стоимость доставки не попадают в стоимость.
При недостоверной цене поле остаётся пустым.
HTML и технический текст не попадают в описание.
Логотип, favicon и техническое изображение не выбираются как изображение товара.
После импорта вариант не создаётся автоматически.
Пользователь видит заполненную форму до сохранения.
Вариант создаётся только после нажатия «Добавить вариант».
При частичном импорте отображается предупреждение.
При ошибке исходная ссылка или текст сохраняются.
Переход к ручной форме сохраняет исходный ввод и найденные данные.
При возврате исходный ввод восстанавливается.
Повторный импорт не создаёт дополнительный вариант.
Данные разных импортов не смешиваются.
Пользовательские изменения не перезаписываются молча.
Повторное нажатие во время загрузки не создаёт второй запрос.
Импортер не обращается к локальным и приватным адресам.
Редирект на приватный адрес блокируется.
Работают timeout, лимит размера ответа и лимит редиректов.
Существующие варианты подарков продолжают работать.
Логика голосования и результат первой итерации не изменены.
11. Целевые тесты

Добавить или обновить только точечные тесты.

Unit-тесты очистки

Проверить:

декодирование &nbsp;, &amp;, &#8381;;
удаление названия магазина из хвоста title;
удаление «купить в Москве» и аналогичных фраз;
удаление повторяющихся частей;
безопасное ограничение длины;
очистку описания;
отказ от неоднозначной цены;
удаление старой цены и доставки;
отклонение favicon и логотипа;
удаление рекламных URL-параметров без изменения пути товара.
Тесты потока

Проверить:

импорт возвращает черновик, а не создаёт вариант;
создание происходит только после подтверждения;
частичный импорт;
неудачный импорт;
ошибка сети;
переход к ручному добавлению;
сохранение исходной ссылки;
повторный импорт;
сохранение пользовательских правок;
отсутствие смешивания старых и новых данных.
Security-тесты

Проверить блокировку:

file://;

Инструкция Kimi для экономии квоты
Выполни только итерацию очистки, подтверждения импорта, сохранения черновика
и безопасности внешней загрузки.

Не реализовывай проверку дубликатов, нормализованный URL для уникальности,
409 Conflict, уникальные индексы или параллельную защиту от дублей.

Не анализируй весь репозиторий.

Сначала найди только текущую цепочку:
ввод ссылки или текста → запрос импорта → результат импорта →
форма «Добавить вариант» → создание варианта.

Работай только с файлами, которые непосредственно участвуют в этой цепочке,
и с их существующими unit-тестами.

Не меняй:
- мобильную компоновку;
- дизайн карточек;
- редактор порядка;
- выпадающие меню;
- общий mobile footer;
- логику голосования;
- переключение «Подарок / Бюджет»;
- ограничения после первого голоса;
- результат первой UI-итерации.

Не переписывай парсер целиком.
Расширь существующую очистку и текущий поток минимальными изменениями.

Результат импорта должен быть черновиком.
Не создавай вариант до явного нажатия «Добавить вариант».

Для повторного импорта различай автоматически импортированные поля
и поля, изменённые пользователем. Не перезаписывай пользовательские
значения без подтверждения.

Состояния черновика по возможности храни на frontend.
Не добавляй миграцию, если требования можно выполнить без изменения БД.

Для HTTP-загрузки добавь точечные ограничения:
- только http/https;
- SSRF-защита;
- проверка каждого редиректа;
- timeout;
- лимит ответа;
- лимит редиректов;
- безопасное логирование.

Не пиши подробный план и не пересказывай ТЗ.
После поиска цепочки сразу вноси изменения.

Запусти только:
1. unit-тесты очистки названия, цены, описания, ссылки и изображения;
2. тест импорта без автоматического создания варианта;
3. тест частичного импорта;
4. тест сохранения исходного ввода при ошибке;
5. тест перехода к ручной форме;
6. тест повторного импорта и пользовательских правок;
7. security-тесты URL, private IP, redirect, timeout и response-size;
8. typecheck только затронутого пакета.

Не запускай:
- весь e2e-набор;
- полный production build;
- тесты незатронутых пакетов;
- повторный анализ всего репозитория.

В конце сообщи только:
- изменённые файлы;
- изменения потока импорта;
- реализованную очистку;
- реализованные ограничения безопасности;
- изменения схемы данных или явно укажи, что миграция не потребовалась;
- запущенные тесты;
- что не удалось проверить.
