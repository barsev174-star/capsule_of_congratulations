# Защита управления открыткой — 2026-09-01

## Итоговая модель

Маршрут `/manage/{cardId}` использует постоянный UUID открытки только как адрес, а не как полномочие. До загрузки имени, поздравлений, фотографий, настроек, статусов и предпросмотра сервер требует одного из акторов:

- organizer: действующая HttpOnly-сессия `organizer_session`, email которой совпадает с нормализованным `cards.organizer_email`;
- admin или moderator: действующая `admin_session` с cookie path `/`;
- support не имеет доступа к управлению открыткой и детальной странице открыток.

Тот же контроль применяется ко всем server actions и API, которые читают приватный preview или изменяют открытку. Идентификатор поздравления сначала проверяется в пределах уже авторизованной открытки, и только затем выполняется изменение — это закрывает межкарточный IDOR.

## Passwordless-вход и владение

Вход организатора остаётся passwordless: одноразовая ссылка действует 15 минут, хранится только как SHA-256 и после использования создаёт 30-дневную HttpOnly/Secure в production/SameSite=Lax сессию с path `/`.

Для пустого черновика первоначальная резервная ссылка позволяет только запросить письмо. Владение закрепляется атомарно после перехода по magic-link, если email открытки всё ещё пуст. Смена владельца запускается текущим владельцем, но применяется только после подтверждения нового email отдельной magic-link.

Для одной открытки может существовать только один ожидающий запрос смены владельца. Создание или повторная отправка нового запроса под транзакционной advisory-блокировкой удаляет прежние неиспользованные transfer-ссылки. Владелец видит ожидающий email после обновления страницы и может повторить отправку либо отменить её; отмена удаляет все неиспользованные transfer-ссылки открытки.

## Постоянный URL и резервные ссылки

- Канонический URL: `/manage/{cards.id}`.
- Preview: `/preview/{cards.id}` и требует тот же actor-check.
- Старые `/manage/{secret}` и `/preview/{secret}` после миграции разрешаются через хешированную запись резервной ссылки; до подтверждения preview переводит на безопасный экран входа, а после входа адрес канонизируется на UUID.
- Токен резервной ссылки — отдельный 256-битный секрет; в `card_recovery_tokens` хранится только SHA-256.
- Владелец может создать новую резервную ссылку (все прежние отзываются) или отозвать все резервные ссылки, не меняя постоянный URL и email-вход.
- Интерфейс получает из хранилища только факт наличия активной резервной ссылки. Исходный секрет показывается один раз непосредственно после создания и доступен для копирования; восстановить его из SHA-256 позднее нельзя.
- Резервная ссылка сама по себе не открывает содержимое и не разрешает мутации.
- Для ещё не закреплённого черновика ссылка служит bootstrap-доказательством: разрешает запросить первичное письмо и закрепить владельца только после magic-link.
- Для уже закреплённой открытки ссылка помогает снова найти открытку и запустить вход на сохранённый email владельца. Она не заменяет organizer-сессию и не помогает обойти подтверждение email.

## Ограничение частоты запросов

- Запрос обычной ссылки для входа ограничен существующим лимитом magic-link на целевой email.
- Вход через `/manage/{cardId}` и старую резервную ссылку дополнительно ограничен по сочетанию клиента и открытки.
- Запрос смены email владельца ограничен по открытке: по умолчанию не более 5 корректных попыток за час (`MANAGE_EMAIL_CHANGE_RATE_LIMIT`). Отдельно продолжает действовать лимит magic-link на каждый целевой email.
- После успешной отправки интерфейс блокирует повторное действие на 60 секунд и показывает обратный отсчёт. Это UX-защита от случайных повторов; серверные лимиты остаются обязательными и не зависят от состояния браузера.

## Локальная разработка без письма

На экране подтверждения в development показывается действие «Войти без письма». Сервер создаёт organizer-сессию напрямую только при одновременном выполнении двух условий:

- `NODE_ENV` не равен `production`;
- заголовок `Host` указывает на `localhost`, `127.0.0.1` или `[::1]`.

В production обход отклоняется до чтения открытки даже при запуске на loopback. Для первичного закрепления пустого черновика локальный обход всё равно требует действующую резервную ссылку и корректный email.

## Миграции и выпуск

Миграции должны применяться строго по порядку:

1. `0037_organizer_magic_link_context.sql` добавляет безопасный return path, первоначальное закрепление и подтверждаемую передачу владельца.
2. `0038_card_recovery_tokens.sql` создаёт таблицу recovery-токенов, хеширует существующие `cards.manage_token`, переносит их и очищает plaintext-колонку.

Перед `0038` обязателен проверенный backup PostgreSQL. После применения старый код, который ищет `cards.manage_token`, нельзя использовать для rollback без восстановления базы из backup; код и схема должны откатываться вместе. Новому коду nullable legacy-колонка не нужна для авторизации.

## Проверка после deploy

1. Анонимное открытие `/manage/{cardId}` показывает только экран подтверждения без приватных данных.
2. Сессия другого organizer получает экран смены аккаунта и не может вызвать server action/API.
3. Владелец после magic-link открывает `/manage/{cardId}` и `/preview/{cardId}` после refresh и в новой вкладке.
4. Admin и moderator открывают управление с заметным служебным banner; support получает отказ.
5. Старая резервная ссылка ведёт к email-подтверждению, после входа URL заменяется на постоянный.
6. После создания новой резервной ссылки старая не работает; после отзыва не работает ни одна.
7. Поздравление из другой открытки нельзя скрыть, изменить, удалить или переместить через подмену ID.

Автоматические проверки: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, затем штатные migration и production smoke из deploy-runbook.
